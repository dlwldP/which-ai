# AI 뭐 써? 기획서

> 하고 싶은 일별로 쓸 수 있는 AI를 최대한 많이 모아 짧게 알려주는 비개발자용 AI 모음 (2026-11-06 개편)
> 버전: v0.1 (MVP 기획) · 작성: 2026-10-19 · 시리즈: "AWS 얼마야?"의 자매 프로젝트

> 이 문서에서 정하지 않은 세부 사항은 [decisions.md](decisions.md)에 정리했다.

---

> **2026-11-06 개편 (J 결정).** 서비스 목적을 "툴 2~3개를 자세히 비교하는 선택 도우미"에서 "현존하는 AI를 최대한 많이, 용도별로 짧게 알려주는 모음"으로 바꿨다. GPT·Claude처럼 유명한 것 말고도 사람들이 모르는 AI 툴·에이전트·오픈소스를 알리는 게 목적이다. 아래 1~3장, 8~10장은 개편 내용으로 고쳤고, 4~7장·11장 이후의 예전 내용 중 이와 어긋나는 부분은 개편 내용이 우선한다.

## 1. 한 줄 정의

"이미지 만들 땐 뭐가 있지?"에 답하는 사이트. 하고 싶은 일(용도)을 누르면 쓸 수 있는 AI를 카드로 쭉 보여주고, 카드마다 **무료인지 유료인지**, **어떻게 쓰는지**(웹사이트에서 바로 / 앱 설치 / 직접 설치)만 짧게 알려준다.

## 2. 문제와 타깃

| 항목 | 내용 |
| --- | --- |
| 문제 | AI가 너무 많은데 사람들은 GPT·Claude 정도만 안다. 이미지·영상·목소리·번역 같은 일마다 어떤 AI가 있는지, 무료로 되는지 한 번에 보기 어렵다. |
| 타깃 | 직장인, 대학생, 소상공인 등 AI를 써보고 싶은 비개발자 (개발자용은 [개발자용_기획서.md](개발자용_기획서.md)) |
| 차별점 | ① **용도별로 최대한 많이** ② 카드 한 장에 **이름·한 줄 설명·무료/유료·쓰는 방법·공식 링크만** ③ 가격은 **공식 사이트 문장으로 확인**하고, 모르면 "확인 필요"로 표시 ④ 광고·제휴 없음, 이름순 |

## 3. 범위

### 포함

- 용도 5개(글쓰기·질문·자료 조사 / 회의 녹음·번역 / 이미지·발표자료 / 영상·목소리·음악 / AI 비서·웹사이트 만들기)와 용도별 카드 목록. 툴 수 상한 없음, 비개발자용·개발자용 각각 100개 이상 (2026-11-06). 아래 6장의 목적 10개는 예전 기준
- 카드: 이름(공식 사이트 링크), 한 줄 설명, 가격 배지(무료 / 무료 + 유료 / 무료로 시작 / 유료 / 가격 확인 필요), 쓰는 방법, 다른 용도 태그, 확인 날짜, "정보가 틀려요"
- 조건 칩: 무료로 쓸 수 있는 것만, 설치 없이 웹사이트에서
- 이름·설명으로 찾기, 전체 보기
- 용어집, 변경 이력(날짜만), "정보가 틀려요" 제보(구글 폼), 하단 개인정보 처리방침·이용약관·보안 안내, 다크모드, 모바일

### 없앤 것 (2026-11-06)

- 점수 추천과 추천 이유, "자세히 보기", 툴 상세 화면
- 학습 정책, 무료 한도, 유료 가격 숫자, 한국어 점수, 사용 기기 목록, 가입 방법, 시작 3단계, 주의할 점, 목적별 기능 체크리스트

### 절대 하지 않을 것 (Non-goals)

- 런타임 LLM 호출, 서버, 회원가입 (운영비 0원 유지)
- 제휴 링크·광고로 순서를 바꾸는 것
- 확인하지 않은 가격을 추측으로 채우는 것 (모르면 "확인 필요")

## 4. 설계 원칙

1. **추천은 규칙으로**: 사이트에서 LLM을 부르지 않는다. 큐레이션 점수와 조건 필터로 결정론적으로 추천하고, 같은 입력이면 항상 같은 결과가 나온다.
2. **이유 없는 추천 금지**: 추천 카드마다 "왜 이걸 추천했는지" 문장이 최소 1개 있어야 한다. 데이터에서 자동 생성한다.
3. **모르면 모른다고 표시**: 확인 안 된 값은 빈칸이 아니라 "확인 필요"로 표시한다. 90일 넘게 확인 안 된 항목은 배지를 단다.
4. **출처 필수**: 가격·정책 값은 공식 페이지 URL을 `sources`에 남긴다. 출처는 데이터와 검토 체크리스트(`drafts/REVIEW.md`)에 남기고, 화면에는 보여주지 않는다 (2026-11-06).
5. **쉬운 말**: 화면 문구에 영어 약어와 전문용어를 쓰지 않는다. 불가피하면 용어집 툴팁을 단다.

## 5. 사용자 시나리오

1. **회의록**: 팀장이 "회의 녹음을 정리하고 싶다" 선택 + "회사 자료라 보안 중요" → 학습에 쓰지 않는 옵션이 있는 툴 위주로 2개 추천, 각각 "녹음 파일 올리기 → 요약 버튼 → 공유" 3단계
2. **발표자료**: 대학생이 "PPT 만들기" + "무료만" → 무료 한도 안에서 되는 툴 2개, "무료는 한 달 N장까지" 같은 숨은 제한 경고
3. **영상 자막**: 소상공인이 "유튜브 영상 자막" + "한국어 잘 되는 것" → 한국어 품질 상위 툴 추천
4. **잘 모를 때**: "뭘 해야 할지 모르겠어요" → 많이 쓰는 목적 Top 3 바로가기

## 8. 데이터 설계 (2026-11-06 개편)

### `data/tools.json` (툴 1개 예시)

```json
{
  "id": "elevenlabs",
  "name": "ElevenLabs",
  "url": "https://elevenlabs.io/",
  "one_liner": "글을 넣으면 사람처럼 자연스러운 목소리로 읽어줘요",
  "purposes": ["P10"],
  "price": { "free": true, "paid": true },
  "use": ["web"],
  "official_domains": ["elevenlabs.io"],
  "sources": ["https://elevenlabs.io/pricing"],
  "last_verified": "2026-11-06"
}
```

| 필드 | 규칙 |
| --- | --- |
| `purposes` | 이 툴로 할 수 있는 용도(`data/purposes.json`의 id). 하나 이상 |
| `price.free` | 무료로 쓸 수 있는지 (`true` / `false` / `null` = 확인 필요) |
| `price.paid` | 유료 요금제가 있는지 (`true` / `false` / `null`) |
| `use` | 쓰는 방법: `web`(웹사이트에서 바로) / `app`(앱 설치) / `install`(직접 설치, 개발 지식 필요) / `api`(다른 프로그램에 연결) |
| `repo_url` | 소스가 공개된 툴이면 저장소 주소 (선택) |
| `official_domains` | 공식 도메인. `url`과 `sources`는 이 도메인이어야 한다 (저장소 주소는 github.com·gitlab.com·huggingface.co도 허용) |
| `sources` | 확인한 공식 페이지 주소. 화면에는 보여주지 않는다 |
| `last_verified` | 확인한 날짜. 90일이 지나면 카드에 "다시 확인 필요" |

### 근거와 확정

- 초안(`drafts/tools.draft.json`)에는 가격 근거 문장 하나(`evidence`, field `price`)만 남긴다. 가격을 못 찾으면 `price`를 `null`로 두고 그대로 확정해도 된다.
- Claude가 근거 문장을 저장한 공식 페이지 글자와 스크립트로 대조하고, 검사가 통과하면 같은 PR에서 바로 확정한다 (`node scripts/draft.js promote-all --verified 날짜`).

### `data/purposes.json`, `data/glossary.json`, `data/changelog.json`

용도는 `{ id, icon, label, examples }`. 용어집과 변경 이력은 예전과 같다.

## 11. 기술 스택과 배포 (AWSCAL과 동일)

| 영역 | 선택 |
| --- | --- |
| 프론트 | 순수 HTML/CSS/JS, 빌드 없음 |
| 데이터 | `data/*.json` |
| 검증 | JSON 스키마 검사 스크립트 (Node) |
| 테스트 | Node 내장 테스트 러너 (추천 로직, 스키마) |
| 배포 | GitHub Actions → GitHub Pages |
| 자동 점검 | 주간 Action: ① 공식 URL 링크 체크 ② `last_verified` 90일 초과 목록 → GitHub Issue 자동 생성 |

> 가격을 자동으로 긁어오지 않는다. 사이트마다 구조가 달라 깨지기 쉽고, 틀린 값이 자동 반영되는 게 더 위험하다. 자동화는 "확인해야 할 목록을 만들어주는 것"까지만 한다.

## 13. 개발 단계 (바이브코딩 Phase)

| Phase | 목표 | 완료 조건 |
| --- | --- | --- |
| 0. 데이터 | 목적 10개 확정, 툴 30개 공식 페이지 확인 후 `tools.json` 작성 | 스키마 검사 통과, 모든 툴에 출처·확인 날짜 |
| 1. 추천 로직 | `js/recommend.js` 순수 함수 + 테스트 | 12장 테스트 전부 통과 |
| 2. 화면 | 홈, 조건 선택, 추천 결과 | 모바일·데스크톱에서 시나리오 1~4 수동 확인 |
| 3. 상세·부가 | 툴 상세, 용어집, 변경 이력, 다크모드 | 모든 툴 상세 페이지 열림 |
| 4. 배포·자동화 | Pages 배포, 주간 링크·신선도 점검 Action | 일부러 날짜를 오래된 값으로 바꾸면 Issue 생성 확인 |
| 5. 마감 | README, 데이터 기여 가이드, 스크린샷 | 비개발자 3명에게 써보게 하고 피드백 반영 |

> 핵심: **Phase 0이 이 프로젝트의 본체다.** 코드는 단순하고, 가치는 데이터 품질에서 나온다. 바이브코딩에 맡기지 말고 J가 직접 확인해서 채워야 한다.

### Phase별 첫 프롬프트 예시

- **Phase 1**: "CLAUDE.md와 기획서 9장을 읽고 `js/recommend.js`에 추천 함수를 만들어. 입력은 목적 ID와 조건 객체, 출력은 툴 3개와 추천 이유 배열이야. DOM에 접근하지 말고 순수 함수로 만들어. 기획서 12장의 테스트를 `tests/recommend.test.js`에 작성해."
