# 개발할 때 AI 뭐 써? 기획서 (초안)

> "AI 뭐 써?"의 개발자용 버전. 개발 단계(기획 → 만들기 → 배포 → 리뷰)를 고르면 맞는 도구 2~3개를 이유와 함께 비교해준다.
> 버전: v0.1 초안 · 작성: 2026-10-19 · 기준 문서: [AI뭐써_기획서.md](AI뭐써_기획서.md)
> 상태: **J 검토 전.** "결정 필요" 표시가 남아 있다.

---

## 1. 한 줄 정의

"Supabase랑 Firebase 중 뭐 써?", "코드 리뷰 AI 뭐가 있어?"에 답하는 페이지. 비개발자용과 같은 방식(목적 → 조건 → 추천 2~3개 + 이유)으로 개발 도구를 비교한다.

## 2. 비개발자용과의 관계

| 항목 | 비개발자용 (기존) | 개발자용 (이 문서) |
| --- | --- | --- |
| 주소 | `/which-ai/` | `/which-ai/dev/` |
| 타깃 | 직장인, 학생, 부모님 세대 | AI로 앱을 만드는 개발자, 바이브코더, 개발 입문자 |
| 데이터 | `data/tools.json` | `data/dev/tools.json` (따로 관리) |
| 같이 쓰는 것 | 추천 엔진 구조, 검사 스크립트, 초안→확인 흐름, 주간 점검, 디자인 | |
| 연결 | 비개발자 화면 아래쪽에 "개발자라면 → 개발할 때 AI 뭐 써?" 작은 링크 하나 | |

비개발자용 기획서의 Non-goals("개발자용 도구는 다루지 않음")는 **비개발자 화면**에 대한 규칙으로 남긴다. 개발 도구는 개발자용 화면에만 나온다.

## 3. 목적 (하고 싶은 일) 9개

J가 제안한 카테고리를 목적으로 쓴다. ID는 카테고리 ID를 그대로 쓴다.

| ID | 화면 문구 (제안) | 예시 도구 |
| --- | --- | --- |
| planning | 기획하고 같이 일하기 | Notion AI, Linear, Miro |
| app_builders | 말로 설명해서 앱 통째로 만들기 | Lovable, Bolt.new, Replit |
| coding_agents | AI와 같이 코드 짜기 (에디터·에이전트) | Claude Code, Cursor, Codex |
| backend_database | 백엔드·데이터베이스 붙이기 | Supabase, Firebase, PostgreSQL |
| design_ui | 화면 디자인·시안 만들기 | Figma, Stitch, shadcn/ui |
| data_ml | 데이터·모델·검색 증강(RAG) 다루기 | Hugging Face, Ollama, LangChain |
| devops | 배포·인프라·자동 빌드 | Docker, Vercel, GitHub Actions |
| automation | 업무 자동화·에이전트 연결 | n8n 등 (검증된 것만) |
| code_review | 코드 리뷰·품질 검사 받기 | CodeRabbit, Qodo, Sourcery |

- **learning(학습 자료)**은 추천 대상에서 뺀다. 대신 도구마다 `learn` 링크(공식 문서, 튜토리얼, 강좌)를 달아 상세 화면의 "배울 거리"로 보여준다.
- **open_source**는 카테고리가 아니라 **조건**("오픈소스만")과 도구 속성(`open_source`)으로 바꾼다. OpenCode, Aider처럼 오픈소스 도구는 원래 목적(coding_agents 등)에 들어간다.
- 중복 분류 허용: 도구는 여러 목적에 적합도(0~3)를 가진다. **대표 목적**(`primary`)은 하나만 지정한다.

## 4. 조건

| 조건 | 규칙 |
| --- | --- |
| 무료로 시작 가능 | `price.free == true` |
| 오픈소스만 | `open_source == true` |

결과가 0개면 조건을 하나씩 빼고 안내한다. **결정 필요 ①:** 빼는 순서 (제안: 오픈소스 → 무료).

## 5. 데이터 (`data/dev/tools.json`, 도구 1개)

비개발자용과 같은 칸에 아래를 더하고, 일부는 뺀다.

| 필드 | 규칙 |
| --- | --- |
| `primary` | 대표 목적 ID 하나. `purposes`에서 적합도 1 이상이어야 함 |
| `ai_native` | `yes` (AI가 핵심) / `partial` (AI 기능이 일부) / `no` (AI 툴 아님 → "AI와 같이 쓰는 도구" 표시) |
| `open_source` | `true` / `false`. `true`면 저장소 주소(`repo_url`) 필수 |
| `forms` | 쓰는 형태: `web` / `desktop` / `ide_extension` / `cli` / `library` / `cloud_service` / `self_host` 중에서 |
| `learn` | 배울 거리 링크 목록 `{ "title", "url" }` |
| 그대로 | `id, name, url, one_liner, purposes, price, privacy, start_steps, cautions, sources, last_verified` |
| 빼는 것 | `korean`, `login`, `platforms` (→ `forms`로 대체) |

- `privacy`(입력한 코드를 학습에 쓰는지)는 조건으로 쓰지 않지만 **비교 항목으로 보여준다.** 모르면 "확인 필요".
- **결정 필요 ②:** `korean`(한국어 지원)을 뺄지. 개발 도구는 대부분 영어라 비교 의미가 적다고 보고 빼는 쪽을 제안.

## 6. 추천 점수

```
점수 = purposes[P] × 10
     + (ai_native == "yes" ? 2 : 0)
     + (price.free ? 2 : 0)
     - (최종 확인 90일 초과 ? 3 : 0)
상위 3개, 동점이면 이름순
```

- **결정 필요 ③:** `ai_native` 가산점을 둘지. 사이트 이름이 "AI 뭐 써?"라서 AI 도구를 조금 앞에 두는 쪽을 제안. 단, backend_database·devops처럼 AI 툴이 거의 없는 목적에서는 AI가 아닌 도구가 나와도 된다.
- 추천 이유 문장: 기존 템플릿 + "오픈소스예요", "AI 툴은 아니지만 AI로 만든 앱에 자주 같이 써요"(ai_native=no).

## 7. 화면

비개발자용과 같은 구성(홈 → 조건 → 결과 카드 → 상세)과 디자인을 쓴다. 다른 점:

- 카드 비교 항목: 무료로 쓰기 / 유료 가격 / 오픈소스 / 쓰는 형태 / 코드 학습 정책 / AI 여부
- 상세 화면에 "배울 거리"(`learn`) 목록
- **결정 필요 ④:** 화면 문구 수준. 비개발자용은 "영어 약어 금지"였지만, 개발자용은 CLI, IDE, RAG, CI/CD 같은 용어를 그대로 쓰고 용어집으로 보충하는 쪽을 제안.

## 8. 데이터 채우는 방식

비개발자용과 같다: Claude 초안(`drafts/dev-tools.draft.json`, 공식 도메인 근거) → J 확인 → `promote`.

- `learn` 링크는 공식 문서 외에 강좌 사이트(예: 부스트코스)도 올 수 있어서, **결정 필요 ⑤:** 허용할 외부 학습 사이트 목록을 J가 정한다.
- 확인 안 된 도구는 넣지 않는다. 예: "Paperthin"은 공식 사이트로 존재와 성격을 확인한 뒤 결정.
- 상한: 목적당 5개, 전체 45개 (목적 9개 × 5).

## 9. 하지 않을 것

- 비개발자 화면에 개발 도구 섞기
- AI 툴이 아닌 것을 AI 툴이라고 소개하기 (`ai_native`로 구분해서 표시)
- 학습 자료를 도구처럼 추천 순위에 넣기
- 런타임 LLM 호출, 서버, 광고·제휴 링크 (기존과 동일)

## 10. 개발 단계 (제안)

| 단계 | 내용 |
| --- | --- |
| D0 | 이 기획서 확정 (결정 ①~⑤) |
| D1 | `data/dev/` 스키마 + 검사 + 추천 엔진을 두 데이터 세트에서 쓰도록 일반화 + 테스트 |
| D2 | `/dev/` 화면 (기존 화면 코드 재사용), 예시 데이터로 확인 |
| D3 | 초안 → 확인 흐름, 주간 점검에 개발자용 데이터 추가 |
| D4 | 실제 도구 데이터 채우기 (목적별로) |
